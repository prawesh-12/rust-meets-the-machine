What is inside a process's address space?

Each process gets its own address space: the range of addresses its instructions can use. Here is one opened up, using the memory map of a real Rust program.

  • Rust language
  • Compiler & runtime library
  • Operating system
  • CPU & hardware

A virtual address is a number an instruction uses to name a byte, such as [rsp+8] in a load instruction. It only has meaning inside one process. With virtual memory, every memory access a program makes uses a virtual address kernel docs, and the hardware translates it to a physical one behind the scenes.

The address space is the whole range of those numbers. On x86-64 Linux, the part a program may use runs from 0 to about 128 TiB x86-64 mm docs. That is far more than any computer's RAM, so almost all of it is empty. Only some ranges are mapped: the kernel has recorded what they are for and what may be done with them.

A real map

On Linux, every process can read its own map from the file /proc/self/maps. Each line is one mapping: an address range, permissions, and what backs it proc_pid_maps(5). The program below creates two vectors and a second thread, prints a few addresses, then prints its own map.

examples/maps.rs (shortened)run on Linux x86-64 
let small = vec![10, 20, 30];          // 12 bytes of elements
let big = vec![0u8; 1 << 20];          // 1 MiB of elements
let local = 7;
let h = thread::spawn(|| { let t = 1; println!("{:p}", &t); … });
println!("{:p}", small.as_ptr());       // where each thing ended up
println!("{:p}", big.as_ptr());
println!("{:p}", &local);
print!("{}", fs::read_to_string("/proc/self/maps")?);

The figure draws that map with low addresses at the bottom, as the numbers grow upwards. Empty stretches between mappings are drawn as hatched gaps; they are huge, and drawing them to scale would make the mappings invisible. Click a region to see what lives there and who manages it.

Reading the map

Look at what a "process" turned out to be. It is not one block with a stack at one end and a heap at the other. It is a collection of separate mappings.

This one has the executable in four pieces, three shared libraries and a [heap] range. It also has two stacks (one per thread), a large anonymous mapping holding one vector, and a few pages the kernel supplies. Each mapping has its own permissions:

  • r read, w write, x execute, or - for "not allowed";
  • p private (copy-on-write) or s shared with other processes.

Machine code is r-x: readable and executable, but not writable. Data is rw-: writable but not executable. A program might try to write to its own code, or jump into its data. Both break those permissions, and the hardware stops the program, using permission bits kept in the page table.

Two of the printed pointers deserve attention. small's 12-byte buffer is in [heap]. big's 1 MiB buffer is in a mapping of its own. Both are "on the heap" in the Rust sense, because both came from the allocator Allocator. The allocator chose where to put each one, and for large blocks glibc asks the kernel for a fresh mapping. The label [heap] in the map names one particular range, not every heap allocation.

A tempting picture that is wrong

"A process has one stack at the top and one heap at the bottom, growing towards each other." That is a common textbook drawing of an old, single-threaded process. A real process has a stack per thread, several heap-like areas, and many other mappings in between.

Mapped is not the same as in RAM

The address space is about 128 TiB. A laptop has perhaps 16 GiB of RAM. Even mapped ranges are not necessarily using RAM. When the kernel maps an anonymous range, it only reserves the addresses; it gives a page real memory the first time the program writes to it kernel docs. This is called demand paging.

You can watch it happen. examples/rss.rs creates a 64 MiB vector of zeros, then writes one byte into every 4096-byte page. Before and after the writes, it reads the kernel's count of resident memory (Rss) for that mapping:

Moment Mapped size Resident in RAM
After vec![0u8; 64 << 20] 65 540 kB 4 kB
After writing one byte per page 65 540 kB 65 536 kB

Real run, values from /proc/self/smaps, Linux x86-64. Exact numbers depend on the kernel and allocator.

The vector existed, had a length of 64 MiB and could be read, but almost none of it was in RAM until it was written. The address space describes what a process may use. Which parts currently sit in RAM is a separate question. The kernel can change the answer at any time, for example by moving rarely used pages out to swap.

Who decides the layout?

Several parties decide, each for its own part:

  • The linker decides the layout inside the executable.
  • The kernel decides where mappings go, within its rules and with randomisation.
  • The dynamic loader places the libraries.
  • The allocator decides where each heap block goes.
  • The thread library places thread stacks.

Rust the language decides none of this; it does not define a memory map at all. The map shown here is real, but it comes from one machine; other systems lay things out differently.

What to remember

  1. An address space is a set of separate mappings, each with permissions: code, data, libraries, heap areas, and one stack per thread.
  2. "Heap-allocated" means "from the allocator"; the allocator can use [heap] or other mappings.
  3. Mapped addresses are not necessarily backed by RAM; pages get memory when they are first used.

Check your understanding

The 1 MiB vector's buffer is not inside [heap]. Is it still a heap allocation?

Yes. It came from the allocator, which is what "heap allocation" means. For large blocks, glibc's allocator uses a separate anonymous mapping.

Why do the two runs show different addresses for the same regions?

Linux randomises where it places mappings each time a program starts. Each run is a separate process with its own address space anyway, so the numbers were never shared.

A program maps 1 GiB and never touches it. How much RAM does that use?

Almost none. The addresses are reserved, but the kernel gives a page physical memory only when it is first used.
