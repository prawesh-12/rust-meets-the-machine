Who frees a String's memory, and what does let b = a; change?

A String is a 24-byte handle that points to a heap buffer. Copying the handle would give two handles to one buffer, and then both would try to free it. Ownership is the rule set that prevents this, and it is checked entirely by the compiler.

  • Rust language
  • Compiler & runtime library
  • Operating system
  • CPU & hardware

One owner per value

The Book states the rules in three lines The Book §4.1:

  • Each value in Rust has an owner.
  • There can only be one owner at a time.
  • When the owner goes out of scope, the value will be dropped.

"Dropped" means its destructor runs. For a String, that gives the buffer back to the allocator. Because there is exactly one owner, the buffer is freed exactly once: never zero times (a leak) and never twice (a double free).

None of this exists at run time Rust. There is no owner field in memory and no counter. The compiler works out, from the source, which binding owns what and where each drop has to happen, and inserts the calls to the destructors Compiler.

examples/moves.rs (the part the figure follows)
let n = 5;
let m = n;                  // copy
let a = String::from("hi");
let b = a;                  // move
let c = b.clone();          // clone

The documentation of Copy describes the first two rows: "the only difference is whether you are allowed to access x after the assignment. Under the hood, both a copy and a move can result in bits being copied in memory, although this is sometimes optimized away" std::marker::Copy. A move is not a different machine operation from a copy. The difference is a rule about the source binding. A type that owns a resource, like String, cannot be Copy, because two usable copies of the handle would both free the buffer.

When values are dropped, and in what order

The Reference: "When control flow leaves a drop scope all variables associated to that scope are dropped in reverse order of declaration," and only "an initialized variable" is dropped Reference: destructors. A binding that has been moved out of is not initialized any more, so nothing runs for it. examples/moves.rs shows both rules with three values that print when dropped:

Code and output, from examples/moves.rs
let _first  = Noisy("first");
let second  = Noisy("second");
let _third  = Noisy("third");
let _kept   = second;        // declared last, so dropped first
println!("end of main");
end of main
drop second
drop third
drop first

"second" is dropped first because it now belongs to _kept, the last binding declared. It is dropped once, not once for each binding it passed through.

Freeing is not returning memory to the operating system

When b is dropped, String's destructor calls the global allocator's free function Allocator. The allocator usually keeps the block and reuses it for a later allocation. It is not obliged to give anything back to the kernel. glibc's free returns memory to the system only in some cases, such as large blocks that were mapped separately, or free space at the top of the heap malloc(3) mallopt(3). So after a drop, the process's memory use as the operating system sees it often does not go down OS.

Four tempting pictures that are wrong

"A move copies the text." It copies at most the handle. The heap buffer stays where it is, as the addresses above show.

"Assignment always copies" or "assignment always moves." It depends on the type: Copy types are copied and stay usable; others are moved.

"Ownership is tracked by the CPU or at run time." It is a compile-time rule. The machine code has drop calls in fixed places and nothing else.

"Dropping gives memory back to the OS." It gives the block back to the allocator.

What to remember

  1. Every value has exactly one owner; when the owner goes out of scope, the value is dropped, once.
  2. A move transfers ownership and copies at most the value's own bytes; the old binding can no longer be used. Copy types stay usable; clone makes a real duplicate.
  3. Bindings are dropped in reverse order of declaration; dropping gives memory back to the allocator, not necessarily to the OS.

Check your understanding

After let b = a; with a String, how many heap buffers hold "hi"?

One. The handle moved to b; the buffer was not touched.

Why can i32 be Copy but String cannot?

An i32 owns nothing else, so two copies are harmless. Two usable copies of a String handle would both free the same buffer.

In let x = S("x"); let y = S("y");, which is dropped first at the end of the scope?

y: bindings are dropped in reverse order of declaration.
