How can code use a value it does not own?

Moving scores into a function would leave the caller without it. Most code only needs to read or change a value for a while and then give it back. References do that, and the rules around them are what stop a pointer from outliving the memory it points to.

  • Rust language
  • Compiler & runtime library
  • Operating system
  • CPU & hardware

A reference is a small value that holds an address

&scores creates a reference: a value whose content is the address of scores. Creating one is called borrowing. The reference does not own anything, so dropping it frees nothing The Book §4.2. At the machine level a reference is a pointer Compiler; what makes it a reference is the set of rules the compiler checks about it Rust.

&scores points at the 24-byte handle, wherever scores is stored. &scores[0] points into the heap buffer. That difference is why the second kind is affected when the buffer moves. examples/refs.rs printed both addresses and the sizes. &Vec<i32> is 8 bytes, while &[i32] and &str are 16. A reference to a slice is bigger because it also records how many elements it covers.

The two rules

From the Book The Book §4.2:

  • "At any given time, you can have either one mutable reference or any number of immutable references."
  • "References must always be valid."

&T is a shared (immutable) reference: many can exist together, and none of them can change the value. &mut T is a mutable reference: while it exists, it is the only way to reach the value. The first rule means data is never changed while someone else is reading it, which also rules out data races between threads. The second means a reference never outlives what it points to.

How long a borrow lasts

A borrow does not last until the end of the block. The Book: a reference's scope "starts from where it is introduced and continues through the last time that reference is used" The Book §4.2. The compiler checks each pair of borrows whose ranges overlap.

Lifetimes: what a reference may outlive

The second rule, "references must always be valid," is checked with lifetimes: the compiler's name for the stretch of code in which a reference must stay usable. If a value is dropped while a reference to it is still going to be used, the program is rejected:

examples/outlives.rsdoes not compile
let r;
{
    let x = 5;
    r = &x;
}                      // x dropped here
println!("r: {r}");   // r still used
error[E0597]: `x` does not live long enough
  |
5 |         let x = 5;
  |             - binding `x` declared here
6 |         r = &x;
  |             ^^ borrowed value does not live long enough
7 |     }
  |     - `x` dropped here while still borrowed
8 |     println!("r: {r}");
  |                   - borrow later used here

In memory terms, x was in a frame or register that is about to be reused. Returning a reference to a local fails for the same reason. The compiler reports it as a missing lifetime, because the returned reference has nothing it could borrow from:

examples/dangle.rsdoes not compile
fn dangle() -> &String {
    let s = String::from("hi");
    &s                 // s is dropped when dangle returns
}
error[E0106]: missing lifetime specifier
  |
2 | fn dangle() -> &String {
  |                ^ expected named lifetime parameter
  |
  = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from

A lifetime annotation such as 'a in fn first<'a>(v: &'a Vec<i32>) -> &'a i32 does not keep anything alive. The Book: "Lifetime annotations don't change how long any of the references live. Rather, they describe the relationships of the lifetimes of multiple references to each other" The Book §10.3. That signature says "the returned reference is valid for as long as the argument is", so callers can be checked without looking inside the function.

Where checking stops: unsafe

Everything above applies to safe Rust. Rust also has raw pointers, *const T and *mut T, which carry no lifetime and no borrow rules. Creating one is safe; reading or writing through one needs an unsafe block.

Inside it, the compiler trusts you instead of checking. The Reference: "unsafe only means that avoiding undefined behavior is on the programmer" Reference: undefined behavior. Libraries such as Vec use unsafe code internally and expose a safe interface whose rules make misuse impossible from safe code Rustonomicon: how safe and unsafe interact.

Four tempting pictures that are wrong

"A reference is a copy of the value." It holds an address. Reading through it reads the original.

"A lifetime annotation makes a value live longer." It describes a relationship the compiler then checks. It changes no drop.

"Lifetimes are timers that run while the program runs." They exist only during compilation.

"Rust prevents every memory bug." It prevents dangling references and data races in safe code. unsafe code, leaks and logic errors are still possible; see memory bugs and Rust's safety.

What to remember

  1. A reference is a non-owning value that holds an address; dropping it frees nothing.
  2. At any point, a value has either one &mut or any number of &, and a borrow lasts until its last use.
  3. Lifetimes are a compile-time check that no reference outlives its value; unsafe code is where that checking becomes your job.

Check your understanding

Does &scores point to the heap buffer?

No. It points to the Vec handle. &scores[0] points into the buffer.

In the compiling program above, why is let m = &mut scores; on line 5 allowed while r1 and r2 are still in scope?

Their last use is on line 4, so their borrows have ended. Being "in scope" as names does not matter; use does.

Why can't a function return &s for a String it created?

s is dropped when the function returns, so the reference would point at freed memory. The compiler rejects it.
