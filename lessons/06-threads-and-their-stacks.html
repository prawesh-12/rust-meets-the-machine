06Operating system

What do threads share, and what does each keep to itself?

The memory map of a real Rust process can show two stacks: one labelled [stack], and an unlabelled range used by a second thread. A process can run several threads at once. They share almost everything, but each thread has its own stack.

  • Rust language
  • Compiler & runtime library
  • Operating system
  • CPU & hardware

A thread OS is one path of execution through a process: one instruction pointer moving through the code. Each process starts with one thread. It can create more, and the scheduler can run them at the same time on different cores, or take turns on one core.

A thread is very much like a separate process, with one difference. Threads of the same process share one address space, so they can reach the same data OSTEP ch. 26. Linux's documentation puts it plainly: threads "share the same global memory (data and heap segments), but each thread has its own stack" pthreads(7).

What each thread has alone

To follow its own path, each thread needs its own execution state: its own register values, including its own instruction pointer and stack pointer. While a thread runs, those values sit in a core's registers. When the scheduler takes the core away, the kernel saves them, and loads them back when the thread runs again.

Each thread also needs its own call stack. A stack records the chain of calls that are in progress: main called total, which is still running. Two threads are usually in the middle of different calls, so one shared stack could not record both chains. Every thread gets its own region of memory for its stack.

Two threads, one process

This program starts a second thread. Both threads call total on the same vector:

examples/threads_scope.rscompiles · prints 60 60
fn total(values: &Vec<i32>) -> i32 {
    let mut sum = 0;
    for v in values.iter() { sum += v; }
    sum
}

fn main() {
    let scores = vec![10, 20, 30];
    thread::scope(|s| {
        let h = s.spawn(|| total(&scores));   // thread 2
        let a = total(&scores);              // thread 1, at the same time
        let b = h.join().unwrap();
        println!("{a} {b}");
    });
}

Notice what the arrows say. Both threads' total frames point at the same scores, and scores points at the one buffer. Nothing was copied for the second thread. An address means the same thing in every thread of a process, because they all use the same page table. Both threads share the process's address space, but they do not share one call stack.

A thread's stack is not secret from the other threads. It lives in the same address space, so another thread could reach it if it had its address. What is private is the use: only its own thread pushes and pops frames on it. Rust's rules make sure a reference to one thread's stack data cannot be handed to a thread that might outlive it. That is why the example uses thread::scope, which guarantees that the spawned thread finishes before scores goes away.

main is a function, not a stack

People often call the initial thread's stack "the main stack". That is fine as a nickname, but the two words name different things. main is a function. Its call has a frame, near the bottom of the initial thread's stack, above the frames of the start-up code that called it.

The stack belongs to the thread. When main calls total, total's frame goes on the same stack. A second thread never puts its frames there.

How big is a stack?

There is no universal size. On this Linux machine, the initial thread's stack may grow up to 8 MiB, the limit set by ulimit -s; Rust does not choose it std::thread.

For threads made with std::thread, the Rust standard library currently picks a default of 2 MiB on its main platforms. Its documentation says this may change. You can choose another size with Builder::stack_size or the RUST_MIN_STACK variable. The second thread's stack in the real memory map was slightly more than 2 MiB. Other systems and settings give other numbers.

Shared does not mean safe

If two threads can reach the same memory, they can also both write to it at the same moment. When at least one access is a write and nothing orders them, that is a data race, and in Rust it is undefined behaviour Rust Reference. The hardware and the OS will not stop it: from their point of view, two threads writing to their own process's memory is allowed.

Rust stops it at compile time instead Rust. The marker traits Send ("safe to move to another thread") and Sync ("safe to share between threads") Rustonomicon, together with the borrowing rules, decide what may cross between threads. The example compiles because both threads only read scores through shared references. Change one of them to modify the vector, and the compiler refuses.

What to remember

  1. Threads of one process share the address space: code, globals and heap allocations.
  2. Each thread has its own registers and its own call stack.
  3. Sharing memory does not make sharing safe; Rust's Send/Sync and borrowing rules decide what may be shared.

Check your understanding

Thread 2 reads scores[0]. Does it read a copy of the buffer?

No. It uses the same address as thread 1, which leads to the same buffer, because both threads use the process's one page table.

Thread 1 calls a deeply recursive function. Does thread 2's stack fill up too?

No. Each thread has its own stack. Thread 1 can run out of its stack while thread 2's stays as it was.

Is "the main stack" the stack of the function main?

It is the stack of the initial thread. main's frame is one of the frames on it, along with the start-up code's frames and every function main calls.
