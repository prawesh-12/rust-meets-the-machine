05CPU & hardware Operating system

How does a virtual address reach physical RAM?

The addresses a process uses are virtual: by themselves, they name nothing in the RAM chips. On every memory access, hardware connects the virtual address to a place in real memory.

Physical RAM Hardware is the actual memory hardware. It has physical addresses, which select real storage. The program never uses them. It uses virtual addresses, and hardware in the CPU translates each one to a physical address before the access happens Arm memory management guide.

Translating every byte separately would need an enormous table. So translation works on fixed-size blocks.

Pages and frames

The kernel treats physical RAM as a row of equal blocks called page frames kernel docs. The virtual address space is cut into blocks of the same size, called virtual pages. Translation maps a whole virtual page onto a whole frame. Dividing memory this way is called paging. The size depends on the architecture. 4096 bytes is the most common, and it is the size on the machine the examples were run on; Arm also supports 16 KiB and 64 KiB, and both x86-64 and Arm can use much larger "huge" pages.

Because a page and a frame are the same size, a byte's position inside its page is the same as its position inside the frame. That position is the offset. Translation only has to replace the page part of the address.

Splitting an address by hand

The figure uses a tiny made-up machine so the numbers fit on screen: 16-bit addresses and 4096-byte pages. 4096 is 212, so the low 12 bits of an address are the offset, and the remaining top 4 bits are the virtual page number. In hexadecimal each digit is 4 bits, which makes the split easy to see: 

virtual address   0x5010   =  0101 0000 0001 0000
                               ────  ──────────────
                               page        offset
                               0x5         0x010   (byte 16 of the page)

If the page table says page 5 lives in frame 7, the physical address is frame 7 with the same offset: 0x7010. Only the first digit changed. Real x86-64 addresses use 48 or 57 bits, so the page number is 36 or 45 bits long. The idea is exactly the same.

The page table and the MMU

A page table is a data structure, kept in memory by the kernel OS, with one entry per virtual page. Each entry records:

  • whether the page is mapped at all;
  • whether it is currently present in RAM, and if so, which frame;
  • what is allowed: read, write, execute.

Each process has its own page table. When the scheduler switches to a thread of another process, the kernel tells the hardware to use that process's table.

The MMU (memory management unit) is the hardware that uses the table Hardware. On every load, store and instruction fetch it takes the page number, finds the entry, checks the permissions and builds the physical address. The kernel writes the tables; the MMU reads them. The kernel is not involved in a normal access at all.

Reading the table from memory on every access would be slow, so the MMU keeps a small cache of recent translations: the TLB, or translation lookaside buffer kernel docs. If the translation is in the TLB, no table lookup is needed. If not, the hardware walks the page table and stores the result in the TLB for next time OSTEP ch. 19. The TLB holds translations only, never data.

Three things the translator shows

Neighbours in virtual memory are not neighbours in RAM. In process A, pages 4, 5 and 6 sit next to each other, but they use frames 9, 7 and whatever frame the kernel picks later. The program sees one continuous range of addresses. The RAM behind it can be scattered anywhere. This is how the kernel can hand out memory in any free frame without moving anything.

The same address, different memory. Switch to process B and translate 0x5010 again. B's table sends page 5 to frame 12. This is how processes stay separate: each one has its own table.

Page 1, the code, maps to frame 3 in both processes. Read-only code is shared on purpose.

A fault is not always an error. Try "never touched". Page 6 is part of a mapping but has never been written, so it has no frame yet.

The MMU cannot translate it, so it raises a page fault: the CPU stops the instruction and runs the kernel. The kernel looks up the address in the process's list of mappings and sees that it is legal. It gives the page a zero-filled frame, updates the page table, and lets the instruction run again. The program never notices.

This is demand paging, the effect measured in a real process. The same path brings back pages that were moved out to swap, or reads in pages of a mapped file.

Now try "address near 0" or "write to code". Here the kernel finds that the access is not legal: no mapping covers page 0, and page 1 does not allow writes. It sends the process the signal SIGSEGV, and by default the process ends with "Segmentation fault" mmap(2). Same hardware event, different verdict: the kernel decides OSTEP ch. 21.

Two tempting pictures that are wrong

"The TLB is another name for the cache." The TLB caches translations (page → frame). The data caches hold copies of memory contents. A single load can use both, for different jobs.

"A page fault means the program crashed." Most page faults are normal and invisible: first use of a page, a page coming back from swap, a file being read in. Only faults the kernel cannot justify become a crash.

Where this leaves the program

Every address a Rust program uses, whether a stack slot, a Vec buffer or an instruction, goes through this translation. Rust knows nothing about it. The compiler emits instructions with virtual addresses, the kernel keeps the tables, and the MMU does the work on every access. Together they give each process a large, private, continuous-looking memory, built from scattered frames that may not even be in RAM yet.

What to remember

  1. A virtual address is a page number plus an offset; translation swaps the page number for a frame number and keeps the offset.
  2. The kernel writes each process's page table; the MMU reads it on every access, using the TLB to remember recent translations.
  3. A page fault hands control to the kernel, which either fixes the mapping and retries or stops the process.

Check your understanding

With 4 KiB pages, what is the offset of the address 0x4A38, and which page is it on?

The low 12 bits are the offset: 0xA38. The rest is the page number: 0x4. In the toy machine, page 4 of process A is in frame 9, so the physical address is 0x9A38.

What is the difference between a TLB miss and a page fault?

A TLB miss means the translation was not cached; the hardware reads the page table and carries on. A page fault means the page table itself cannot give a usable translation, so the kernel must step in.

Do the pages of a 1 MiB Vec buffer have to sit in neighbouring frames?

No. The buffer is contiguous in virtual memory, which is what Rust guarantees and what the program sees. Each of its pages can be in any frame, or not in RAM at all yet.
