01Compiler & runtime Operating system

What is a program?

Before a program runs, it is only a text file. A compiler turns that text into an executable file, and the operating system turns the file into a running process. Your main runs at the very end of that chain.

  • Compiler & runtime library
  • Operating system
  • CPU & hardware

A program is a set of instructions and data, prepared so a computer can carry them out. That definition hides three different things.

There is the text you write. There is a file the compiler produces. And there is the program while it runs. They are not the same object, and most confusion about memory starts when they get mixed up.

Here is a small Rust program. It is the example used throughout, so the names compute and result keep coming back.

src/main.rs
fn compute(a: i32, b: i32) -> i32 {
    let x = a + b;
    x
}

fn main() {
    let result = compute(2, 3);
    println!("{result}");
}

Source code is text

main.rs is a text file. Its bytes are letters, spaces and braces. A processor cannot do anything with the letters f, n and a space. It only understands machine code: numbered instructions encoded as bytes, such as "add these two registers" or "jump to this address".

So the text has to be translated once, before the program ever runs. That is the compiler's job.

The compiler translates the text, and checks it

rustc is the Rust compiler Compiler. It reads your source in stages. It first splits the text into tokens and builds a tree that represents the program. It then checks types. Later, on an internal form called MIR, it runs the borrow checker, the part that enforces Rust's ownership and borrowing rules rustc dev guide.

Rust's ownership and borrowing rules are checked at this stage, while the program is still being built. If a rule is broken, no executable is produced. When the program runs, nothing in the CPU checks those rules again.

After checking, rustc hands the program to LLVM, which produces machine code for the target, such as x86-64 or 64-bit Arm. A linker then joins your machine code with code from the standard library and writes one file: the executable.

The executable is a file with a loading plan

An executable is not machine code alone. On Linux it uses the ELF format elf(5). Inside are named sections. .text holds the machine instructions. .rodata holds read-only data, such as the text of string literals. .data holds global variables that start with a value, and .bss records globals that start as zero.

The file also carries a plan for the operating system. The ELF header records the entry point: the address where execution starts. The program headers say which byte ranges of the file to place at which addresses, and whether each range may be read, written or executed.

In the build used for the figure, readelf reports an entry point of 0x14e90, and the symbol at that address is called _start. The compute function is four bytes: 8d 04 37 means "add two registers and put the result in a third", and c3 means "return". The CPU runs these bytes directly; it never sees the Rust text.

A tempting picture that is wrong

"Running a program means loading main.rs into memory and executing it line by line." The source file plays no part at run time. You could delete it after building, and the executable would run the same. What runs is machine code produced from it.

Running the file: the kernel builds a process

When you type ./main in a shell, the shell asks the kernel OS to run the file with the execve system call. The kernel then sets up a new program image, with a newly initialised stack, heap and data segments execve(2).

The kernel reads the program headers and maps the listed ranges into a fresh address space. "Maps" does not mean "copies the whole file into RAM now". Modern systems load lazily: a piece of code or data is read from the file when it is first needed OSTEP ch. 4. The result is visible in the address space of a real process.

This executable also names an interpreter, /lib64/ld-linux-x86-64.so.2. That is the dynamic loader. The kernel starts it first, and it maps the shared libraries the program needs, such as the C library. Then it jumps to the program's entry point.

The result is a process: the program while it runs, with its own address space, one thread, and resources the kernel tracks for it. The file on disk is unchanged. Running it twice gives two processes from one file.

Your main is not the first instruction

It is natural to think the operating system jumps straight to your main. It does not. On this build, disassembly shows the chain that runs first:

Start-up chain in the built file · from objdump and nm
_start                    entry point; sets up registers and the stack
 └ __libc_start_main      C library start-up
    └ main                a C-style main that rustc generated
       └ std::rt::lang_start   Rust standard library start-up
          └ main          your function

Your main is the entry point at the language level Rust. The Rust Reference says a crate with a main function can be compiled to an executable. main's return type must implement the Termination trait, and that trait turns main's result into the process's exit status Rust Reference. Everything above it in the chain is start-up code supplied by the C library and Rust's standard library Compiler & runtime.

What can be different on your machine

The steps are the same in spirit everywhere: translate, store a file, ask the OS to start it, run start-up code, call main. The details are not. Windows and macOS use other executable formats and loaders. Addresses change from build to build and, because of address randomisation, from run to run. A program built for a microcontroller may have no operating system and no loader at all.

What to remember

  1. Source text, the executable file and the running process are three different things.
  2. The compiler checks Rust's rules and produces machine code before anything runs.
  3. The kernel builds a process from the file, and start-up code runs before your main.

Check your understanding

You delete main.rs after building. Does the executable still run?

Yes. The executable holds machine code generated from the source. The source file is not read at run time.

Where are Rust's borrowing rules enforced: in the compiler, the OS or the CPU?

In the compiler. The borrow checker runs on MIR while rustc builds the program. If the rules are broken, no executable is produced.

Is the entry point recorded in the ELF header the address of your main?

No. In this build it is _start. Start-up code from the C library and Rust's standard library runs first and then calls your main.
