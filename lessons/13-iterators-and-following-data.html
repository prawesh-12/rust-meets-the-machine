What does a loop over a Vec actually hand you?

The function total in the example program walks through scores with for v in values.iter(). A loop like that combines a buffer, ownership and borrowing. Each step of the loop hands you one item, and the way the loop is written decides what kind of item it is.

  • Compiler & runtime library

An iterator is its own value

An iterator is a value with one important method, next(). Each call returns Some(item), or None when there is nothing left std::iter Rust. The iterator is separate from the Vec: it holds its own position and refers to the buffer, either through a borrow or by owning it. Creating one reads nothing; the documentation calls iterators lazy: "Nothing really happens until you call next" std::iter: laziness.

A for loop is "sugar for iterators" std::iter: for loops. It turns what follows in into an iterator with IntoIterator::into_iter, then calls next() until it gets None Reference: iterator loops.

The three forms

The documentation lists "three common methods which can create iterators from a collection: iter(), which iterates over &T. iter_mut(), which iterates over &mut T. into_iter(), which iterates over T" std::iter: the three forms. Each one makes the iterator borrow or own the Vec in a different way:

The iter_mut loop added 1 to each element in place, the iter loop read them through references, and the into_iter loop took each one out by value. The sizes show the iterator is a value of its own, separate from the 24-byte Vec handle. They are observations of this toolchain, not guarantees.

After into_iter, scores is gone

into_iter(self) takes the Vec by value, so it is a move. Using scores after the loop is rejected:

examples/afterinto.rsdoes not compile 
error[E0382]: borrow of moved value: `scores`
    |
  3 |     let scores = vec![10, 20, 30];
    |         ------ move occurs because `scores` has type `Vec<i32>`, which does not implement the `Copy` trait
  4 |     for s in scores.into_iter() { println!("{s}"); }
    |                     ----------- `scores` moved due to this method call
  5 |     println!("{:?}", scores);
    |                      ^^^^^^ value borrowed here after move

The same happens with plain for s in scores, because the loop calls into_iter on scores itself. Writing for s in &scores calls it on a reference instead, which gives the same items as scores.iter(); for s in &mut scores matches iter_mut().

Why a loop cannot push to the vector it walks

While an iter() loop runs, the iterator holds a shared borrow of scores and a cursor into its buffer. A scores.push(…) inside the loop needs &mut scores, which would conflict, and could move the buffer from under the cursor. The compiler rejects it with error E0502, the same error as any other borrow conflict. In languages without that check, changing a collection while iterating over it is a common source of bugs; Rust turns it into a compile error.

Three tempting pictures that are wrong

"The iterator is the buffer." It is a separate, small value that refers to the buffer.

"A for loop copies the vector." iter() and iter_mut() copy nothing; they hand out references. into_iter() moves the elements out one by one, and still does not copy the buffer.

"The iterator's layout is fixed." Only its behaviour is documented. Its fields and size belong to the standard library and can change.

What to remember

  1. An iterator is a separate value with a position; each next() hands out one item until it returns None.
  2. iter() gives &T and borrows, iter_mut() gives &mut T and borrows mutably, into_iter() gives T and consumes the collection.
  3. A for loop calls into_iter on whatever follows in; &scores and scores behave differently.

Check your understanding

What is the type of s in for s in scores.iter() when scores is a Vec<i32>?

&i32: a reference to an element in the buffer.

Can you use scores after for s in scores { … }?

No. The loop called into_iter on scores, which moved it. Loop over &scores to keep it.

When is the buffer freed in an into_iter() loop?

When the iterator is dropped, after the loop ends. The iterator owned the buffer from the moment it was created.
