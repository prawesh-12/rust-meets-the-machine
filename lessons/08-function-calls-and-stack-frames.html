08Compiler & runtime CPU & hardware

What happens on the stack when one function calls another?

Every thread has its own stack, and the call and ret instructions move its stack pointer. While functions call each other, the stack holds one record, a frame, for every call that has not returned yet. Some values live inside those frames; others only point somewhere else.

  • Rust language
  • Compiler & runtime library
  • Operating system
  • CPU & hardware
examples/calls.rsprints 10 
fn add(a: i32, b: i32) -> i32 {
    a + b
}

fn average(x: i32, y: i32) -> i32 {
    let s = add(x, y);
    s / 2
}

fn main() {
    let x = std::hint::black_box(13);   // stops the compiler from computing the answer in advance
    let m = average(x, 7);
    println!("{m}");
}

Each time a function is called, it gets a stack frame: a block of the thread's stack for the things that call needs to keep while it runs. Together the frames form the thread's call stack. Giving out memory by moving one pointer like this is called stack-based allocation. A frame can hold:

  • the return address: where to continue in the caller once this call finishes;
  • local values that the compiler decided to keep in memory rather than in registers;
  • saved copies of registers the function needs to reuse, and padding to keep the stack aligned.

Calls nest, so frames nest. The newest frame is always the one that finishes first: last in, first out. On x86-64 the stack grows towards lower addresses, so in the picture new frames appear below older ones System V psABI §3.2.

What the compiler actually produced

The picture is read from the debug build's assembly (-C opt-level=0). Here are the two small functions, from examples/OUTPUT.txt Compiler:

Unoptimised x86-64, Intel syntax, symbol names shortened 
add:
    push  rax                    ; reserve 8 bytes (also keeps rsp 16-byte aligned)
    add   edi, esi               ; a + b, arguments arrived in edi and esi
    mov   dword ptr [rsp + 4], edi
    seto  al
    jo    .overflow              ; debug builds panic on i32 overflow
    mov   eax, dword ptr [rsp + 4]   ; return value goes in eax
    pop   rcx                    ; give the 8 bytes back
    ret                          ; pop the return address and jump there

average:
    push  rax
    call  add                    ; pushes the return address, jumps to add
    mov   dword ptr [rsp + 4], eax   ; s
    …                            ; check for the i32::MIN / -1 case, then divide
    idiv  ecx
    pop   rcx
    ret

Which registers carry arguments and the return value is fixed by a calling convention. For C-compatible functions on Linux x86-64 that is the System V ABI: first integer argument in rdi, second in rsi, result in rax System V psABI §3.2.3. Plain Rust functions use the "Rust" ABI, and the documentation does not specify which registers it uses fn: ABI compatibility. In this build it happened to use the same registers. Treat that as an observation.

With optimisation, the frames are gone

Built with -O, the whole chain becomes a few instructions inside main:

Optimised (-O), the part of main that replaces both calls 
    mov   eax, dword ptr [rsp]   ; x = 13
    mov   ecx, eax
    add   eax, 7                 ; x + 7
    shr   eax, 31                ; sign fix-up for division by 2
    add   eax, ecx
    add   eax, 7
    sar   eax                    ; / 2
    mov   dword ptr [rsp + 4], eax   ; m

The optimised output contains no average or add symbol and no call to either. The compiler inlined them. The behaviour Rust promises is the printed 10, not the number of frames. Frames, slots and calls are decisions of the compiler Compiler, not rules of the language Rust.

Frames are not ownership

A stack frame is a run-time record of one function call Compiler OS. Rust's ownership rules answer a different question: which binding is responsible for a value, and who may use it Rust. A value owned by main can live on the heap, and a value in a frame can be owned by nobody in particular, like the return address. Ownership is a separate picture, drawn on top of this one.

Returning does not clear anything

ret pops the return address and jumps to it. That is all Intel SDM Vol. 2, RET. The returned frame's bytes stay as they were until a later call writes over them, which happens at step 7 above. Safe Rust never lets you read that leftover memory: a reference to a local cannot outlive the function.

Recursion is the same thing, repeated

A function that calls itself gets a new frame for each call that has not returned yet. A recursion 10,000 levels deep needs 10,000 frames at once. The main thread's stack on this machine is 8 MiB (ulimit -s prints 8192), and once frames reach its end the program crashes. That crash is a stack overflow.

Three tempting pictures that are wrong

"Every local variable has a slot on the stack." Above, even the debug build keeps x, y, a and b in registers only. The optimised build keeps almost nothing in memory.

"Returning wipes the function's memory." The stack pointer moves; the bytes stay until something overwrites them.

"main is the stack." main has one frame on the main thread's stack, with start-up frames above it. Other threads have their own stacks.

What to remember

  1. Each call that has not returned has a frame on its thread's stack; frames come and go last in, first out.
  2. A frame holds a return address and whatever the compiler chose to keep in memory. Many values live only in registers.
  3. Returning moves the stack pointer back; it does not erase the old frame's bytes.

Check your understanding

While add runs, how many return addresses for this program's own functions are on the stack?

Two: one back into main (pushed when main called average) and one back into average (pushed when it called add). Above main there are more, from the start-up code.

After average returns, is the value 20 still in memory?

In this debug run, yes, in average's old slot and in add's, until the println! calls reuse that space. Nothing in safe Rust can read it.

Does an optimised build of this program have a frame for add?

No. add was inlined into main, so there is no call, no return address and no frame for it.
