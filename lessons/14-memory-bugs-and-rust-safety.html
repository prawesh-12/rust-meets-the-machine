14Rust Operating system

How do memory bugs happen, and what does Rust change?

Rust's compiler rejects programs that break its ownership and borrowing rules. Those rules exist because of real memory bugs. For each bug, here is what the machine does when it happens, and whether Rust stops it at compile time, at run time, or not at all.

  • Compiler & runtime library
  • Operating system
  • CPU & hardware

Two kinds of failure

Keep two outcomes apart:

  • A panic is a controlled stop. Rust detects the problem, prints a message, by default unwinds the thread, running destructors on the way The Book §9.1. A panic in the main thread ended the examples here with exit status 101. Nothing was corrupted; the program refused to continue.
  • Undefined behaviour means the language makes no promise at all about what happens next. The program might crash, appear to work, or silently corrupt data. Safe Rust is designed so that it cannot cause undefined behaviour; the list of what counts is in the Reference Reference: undefined behavior. In C, out-of-bounds access and use-after-free are undefined behaviour, and the language does not describe stack overflow at all.

1. Stack overflow

Every call that has not returned keeps a frame on the thread's stack. A thread's stack has a fixed maximum size: 8 MiB for the main thread on this machine (ulimit -s), and 2 MiB by default for threads Rust spawns std::thread: stack size. Below the stack is a guard page: memory that is deliberately not mapped, so touching it causes a page fault the kernel cannot resolve OS. Running into it is a stack overflow.

examples/recurse.rs outputexit status 134
thread 'main' (…) has overflowed its stack
fatal runtime error: stack overflow, aborting

What the code intended

Recurse ten million levels and add up the results.

What C allows

The same deep recursion. Usually the guard page stops it with a segmentation fault. A very large frame can step over the guard page entirely and write into other memory, which is undefined behaviour.

What Rust does

Compiles it: stack depth is not checked at compile time. The fault in the guard page is caught by a handler that the standard library installs, which prints the message above and aborts std source: stack_overflow.rs.

So Rust does not make deep recursion safe to run; it makes running out of stack a clean crash instead of memory corruption. Exit status 134 is 128 + 6, the signal SIGABRT. An earlier version of this example used count_down(n + 1) + 1. Built with -O, it never overflowed at all: the optimiser turned the recursion into a loop, and the program ran forever. Whether recursion uses stack is the compiler's decision.

2. Reading past the end of a buffer

scores has 3 elements. Element 10 would be 40 bytes past the start of the buffer, in memory that belongs to something else or to nothing.

examples/index.rs: i is 10, computed at run timeexit status 101
println!("{:?}", v.get(i));
println!("{}", v[i]);
None

thread 'main' (…) panicked at index.rs:5:21:
index out of bounds: the len is 3 but the index is 10

What the code intended

Read element 10, assuming there is one.

What C allows

Reads whatever bytes are 40 bytes past the start, with no check. A write there corrupts another object. This is the classic buffer overflow.

What Rust does

Indexing a slice or Vec checks the index against the length at run time; if the check fails the thread panics Reference: indexing. get returns None instead slice::get.

The bounds check is a compare and a branch before the load. In loops like the one in total, the compiler can often prove the index is always in range and remove the check. Iterators never need one per element.

3. Using memory after it was freed

A use-after-free reads or writes through a pointer whose memory has already been given back. The allocator may have handed that block to someone else, so the read sees their data and the write damages it.

What the code intended

Keep a reference to element 0, push, then read element 0 through the reference.

What C allows

Exactly that. If the push moved the buffer, the read uses freed memory: undefined behaviour, often a silent wrong value.

What Rust does

Rejects it at compile time (E0502, a borrow conflict). Returning a reference to a local (E0106) and keeping one past its owner's scope (E0597) are rejected the same way. A double free is ruled out by single ownership.

This class of bug is stopped before the program runs, with no run-time cost. The price is that some correct programs are rejected too: holding &scores[0] across a push is rejected even in a run where the buffer would not have moved.

What unsafe changes

Inside an unsafe block you can dereference raw pointers, and the compiler no longer checks that they point to live memory. Accessing "a place that is dangling" is undefined behaviour Reference: undefined behavior, and so is a data race. Writing unsafe does not switch the rules off; it makes keeping them your job instead of the compiler's. This site's examples contain no unsafe code, and none of them demonstrate undefined behaviour, because its outcome would prove nothing.

What safe Rust does not promise

The Reference lists behaviour that is wrong but not unsafe Reference: behavior not considered unsafe. Among them:

  • Leaks. Memory that is never freed. std::mem::forget is a safe function, because "Rust's safety guarantees do not include a guarantee that destructors will always run" std::mem::forget.
  • Deadlocks between threads.
  • Integer overflow. Debug builds panic (the debug build of add contains a jo instruction for exactly this); release builds may wrap around silently Reference: overflow.
  • Stack overflow, panics, and wrong results from wrong logic.

Three tempting pictures that are wrong

"Rust makes recursion safe." Deep recursion still runs out of stack. Rust turns that into a clean abort.

"Rust catches every memory bug in every program." It rules them out in safe code. unsafe code, and the libraries it lives in, still need care.

"A panic is memory corruption." A panic is the opposite: a check that fired before anything was corrupted.

What to remember

  1. Out-of-bounds indexing panics at run time; use-after-free and double free are rejected at compile time; stack overflow becomes an abort.
  2. A panic is a controlled stop. Undefined behaviour is the absence of any promise, and safe Rust cannot cause it.
  3. Leaks, deadlocks, integer overflow and stack overflow are still possible in safe Rust.

Check your understanding

Is v[10] on a 3-element Vec a compile error?

Not when the index is only known at run time. It compiles, and the bounds check panics when it runs. With a constant index on an array, the compiler can catch it earlier.

Can safe Rust leak memory?

Yes. std::mem::forget and reference-counted cycles both leak, and both are safe. Leaks waste memory but do not corrupt it.

Why does recurse.rs exit with status 134 rather than 101?

A stack overflow is not turned into a panic. The handler prints a message and aborts the process, and 134 = 128 + 6 (SIGABRT). A panic in the main thread exits with 101.
