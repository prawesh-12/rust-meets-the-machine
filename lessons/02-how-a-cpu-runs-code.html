02CPU & hardware

How does a CPU run code?

The compiler turned compute into four bytes of machine code inside the executable file. A CPU reads bytes like these as instructions and carries them out, one after another.

  • Compiler & runtime library
  • Operating system
  • CPU & hardware

A CPU Hardware does not see functions, variables or types. It sees a stream of instructions. Each instruction is a few bytes that ask for one small action. Typical actions are adding two numbers, comparing two numbers, copying a value from or to memory, and continuing at a different address. A Rust function becomes a short run of such instructions.

Registers: where the CPU keeps the values it is working on

Most instructions do not work on memory directly. They work on registers: a small set of storage slots inside each core, each holding one value of 64 bits on a 64-bit CPU. Instructions name registers directly, so reaching one costs almost nothing. The names depend on the architecture. On x86-64 there are sixteen general-purpose registers such as rax, rdi and rsi Intel SDM vol. 1. 64-bit Arm has thirty-one, called x0 to x30.

Three registers matter for everything that follows:

  • The instruction pointer holds the address of the next instruction. x86-64 calls it rip; Arm calls it the program counter, PC. Running a program means: read the instruction at this address, carry it out, move the pointer on.
  • The stack pointer, rsp on x86-64, holds the address of the top of the current thread's stack.
  • The flags register records facts about the last result, such as "it was zero" or "it overflowed". A later instruction can branch on them. That is how an if or a loop is built.

The actual arithmetic happens in the execution units. The simplest picture is one ALU that takes two inputs and produces a result. Real cores have several units working at once.

Fetch, decode, execute: a model, not a blueprint

The figure uses the classic fetch–decode–execute model. The core fetches the bytes at the instruction pointer, decodes them into an operation, executes it, moves the pointer on, and repeats.

It is the right first picture, and the results it predicts are the results you get.

It is not how a modern core is built. A current x86-64 or Arm core fetches and decodes several instructions per cycle and sends them to many execution units. When one instruction is waiting for memory, the core can finish later ones first, out of order. Different instructions take different amounts of time. The hardware makes sure the program sees the same results as if each instruction had run one after another.

Control flow: calls, returns and loops

Normally the instruction pointer moves to the next instruction. A few instructions change it on purpose. A jump sets it to another address. A conditional branch does so only if the flags say so, which is how if and loops work: a loop is a branch back to an earlier address.

A call saves the address of the next instruction and jumps; a return jumps back to the saved address. Steps 3 and 5 of the figure show that pair. On x86-64 the saved address goes on the thread's stack.

Why the CPU still needs memory

If registers are so fast, why use memory at all? Because there are only a handful of them. A program has far more data than that: a Vec of a million numbers, the text of every string, the machine code itself.

Registers hold what the core is working on right now. Everything else lives in memory, and instructions copy values in (a load) and out (a store) when they need them. In the figure, steps 1, 2 and 6 are exactly that.

The CPU and RAM are separate parts. RAM sits outside the core, and reaching it takes far longer than reaching a register. That gap is why CPUs have caches.

A variable is not always a box in memory

It is tempting to imagine that every let creates a small box in RAM. The optimised compute above shows otherwise: x exists only as a value in eax. Build the same function without optimisation and you get a different picture:

compute built with -C opt-level=0 · real output
push  rax                     reserve 8 bytes of stack
add   edi, esi                a + b
mov   dword ptr [rsp + 4], edi   x gets a stack slot
seto  al
jo    .LBB8_2                 overflow? jump to the panic
mov   eax, dword ptr [rsp + 4]   read x back as the return value
pop   rcx
ret

Here x does get a slot on the stack, and there is an extra check: Rust panics on integer overflow in debug builds, so the code jumps to a panic if the addition overflowed Rust Reference. Same source, two different sets of instructions. Both are correct, because both produce the same result. Rust promises what your program does, not which register or memory slot a variable uses Rust Reference.

What to remember

  1. The CPU runs machine instructions. Each one is a small step on registers or memory.
  2. The instruction pointer says what runs next; calls, returns and branches change it.
  3. A variable may live in a register, in memory, or nowhere at all after optimisation.

Check your understanding

Does the CPU know that x is called x?

No. Names exist in the source and in debug information. The instructions only mention registers and addresses. In the optimised build, x is only the value that ends up in eax.

After call, how does ret know where to go back to?

call wrote the address of the next instruction onto the stack. ret reads it back and puts it in the instruction pointer.

Is "one instruction per clock tick, one after another" an accurate description of a modern CPU?

No. It is a teaching model. Real cores overlap many instructions and can finish them out of order. They guarantee that the results match the one-at-a-time model.
