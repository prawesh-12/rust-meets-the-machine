07CPU & hardware

Where do the bytes of one memory read come from?

A memory read has two halves. The virtual address is translated into a physical one, and then the bytes have to come from somewhere: a CPU cache, or RAM. Here is one load from start to finish.

Take one instruction from the loop in total: reading scores[1]. On x86-64 it might look like mov eax, dword ptr [rdi + 4]: register rdi holds the address of the buffer, and the element is 4 bytes further on. In one recorded run of the example, the buffer started at 0x579e63956d50, so this load asks for the 4 bytes at 0x579e63956d54.

Two separate jobs have to happen before eax holds 20:

  1. Translation: find the physical address for that virtual address.
  2. Data lookup: get the 4 bytes stored at that physical address.

The second job is where caches come in.

Registers, caches, RAM

Three kinds of storage are involved, and they do different jobs Hardware.

  • Registers are part of the core's execution state. Instructions name them directly.
  • RAM holds the contents of physical memory. It is large and, measured in CPU time, far away: a trip to RAM can cost as much time as hundreds of simple instructions Drepper §3.
  • Caches sit between the two. They are small, fast memories inside the CPU that keep copies of recently used parts of RAM. Each cache is usually a level: L1 is smallest and fastest and is checked first; L2 is bigger and slower; L3 is bigger and slower again, and often shared by several cores.

Caches do not store single bytes. They store cache lines, fixed-size blocks of memory. When a byte is needed, its whole line is brought in. On the laptop the examples were run on, a line is 64 bytes (getconf LEVEL1_DCACHE_LINESIZE).

The fast path and the slow path

Most loads in a program like total take the fast path: TLB hit and L1 hit. The loop walks through memory in order. After the first element of a line arrives, the next few are already in L1. Every element in the same 4 KiB page reuses the same TLB entry OSTEP ch. 19.

Data close together in memory and used close together in time is the pattern caches reward. It is called locality.

The slow path is a miss at every level, so the line has to come from RAM. If the TLB missed too, the page tables have to be read first. Each step down the memory hierarchy costs more time. Exact costs depend on the CPU, so no numbers are given here. Drepper's 2007 measurements show the pattern: a few cycles for L1, around ten for L2, and hundreds for main memory Drepper §3.3.

Who moves data into the cache?

Not your program. There is no Rust statement, and normally no instruction in your program, that says "put this in L1". The cache hardware decides what to keep and what to evict, on every access Drepper §3.

Architectures do offer special instructions for hints and for flushing lines, and kernels use some of them. Ordinary code only influences the cache indirectly, through the order in which it touches memory. The cache is a hardware layer beneath your program's memory model; it does not decide Rust ownership.

Not every CPU looks like this

L1/L2/L3 is a common arrangement, not a rule. The laptop the examples were run on has two kinds of core. lscpu reports 8 L1 data caches (one per core), but only 5 L2 caches and 1 L3. Each fast core has its own L2, the four efficiency cores share one L2 between them, and all eight share the L3. Other chips have two levels, or four, or share them differently. Two tempting pictures that are wrong

"The CPU asks RAM for every value." Most loads in ordinary code are served by a cache, and many values never leave registers at all.

"The TLB is the first-level cache." The TLB holds translations. The L1 data cache holds memory contents. A load uses both, for different jobs.

What to remember

  1. A load has two jobs: translate the address (TLB, page tables) and fetch the data (caches, RAM).
  2. Caches hold copies of memory in lines, and the hardware decides what they hold.
  3. Cache levels, sizes and sharing differ between CPUs; L1/L2/L3 is only the common case.

Check your understanding

A load gets a TLB hit and an L1 miss. Was the page table read?

No. The TLB supplied the translation. The L1 miss only means the data has to come from a lower cache level or from RAM.

Why is summing a Vec in order usually fast?

Its elements are next to each other. Each cache line brings several elements at once, and each 4 KiB page needs only one TLB entry, so most loads hit.

Does the Rust compiler decide which values stay in the L1 cache?

No. The compiler decides which values stay in registers and which go to memory. Which memory lines are cached is decided by the hardware at run time.
