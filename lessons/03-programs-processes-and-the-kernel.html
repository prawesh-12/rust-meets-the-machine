03Operating system

What does a program get when it starts running?

A computer runs many programs at once, sometimes the same program several times. Each CPU core follows only one stream of instructions at a time. The kernel keeps the programs apart and shares the cores between them.

  • Compiler & runtime library
  • Operating system
  • CPU & hardware

That something is the operating system, and specifically its kernel OS. The kernel is the part that runs with full control of the hardware. Ordinary programs run with limited rights. When they need something only the kernel may do, such as open a file, start a thread or get more memory, they ask through a system call. The CPU switches into the kernel, the kernel does the work, and the CPU switches back.

A program is a file; a process is a program running

An executable file is a program: instructions and data, stored in a file, doing nothing. A process is one running instance of it. Start the program twice and you have two processes made from one file.

When the kernel creates a process, it gives it:

  • An address space: the range of addresses its instructions can use, and a record of what each part of that range is connected to. The address space shows what fills that range, and address translation connects it to RAM.
  • At least one thread: a path of execution with its own registers and its own stack. The first one is created with the process.
  • Resources the kernel tracks for it, such as a process ID, open file descriptors, the current directory, and resource limits.

Linux documents which of these belong to the whole process and which belong to each thread pthreads(7). Other systems keep similar records in their own way; Windows, for example, calls open files "handles". The idea is the same, the bookkeeping differs.

Same program, two processes, separate memory

Here is the key property. Each process gets its own address space. The same numeric address can appear in both processes and mean two different pieces of memory. On Linux, one process can create another with fork. The two then "run in separate memory spaces": they start with the same contents, but a write in one does not affect the other fork(2).

The figure shows this with small, made-up addresses. Both processes store scores[0] at the virtual address 0x5000. Try writing to it in one process.

Two details in the figure are worth a second look. The data at 0x5000 uses frame 7 in A and frame 12 in B, so a write in A cannot change B. The code at 0x1000 uses the same frame 3 in both. Code is read-only, so sharing it is safe, and it saves memory. The kernel can share or separate memory page by page; separation is the default for a process's private data.

That separation is called process isolation. A bug in one process cannot reach into another process's private memory, even if it writes to a random address. No address in its own space leads there. Processes can share memory on purpose, through shared mappings, but only when both ask for it.

A tempting picture that is wrong

"An address is a position in the RAM chips, so address 0x5000 is the same place for every program." It is not. The addresses a program uses are virtual: they are only meaningful inside one process. The hardware translates them to physical locations using tables the kernel maintains for each process.

Sharing the cores: the scheduler

A laptop may have eight cores and a few hundred threads that want to run. The kernel's scheduler decides which runnable thread uses each core, and for how long.

To switch a core from one thread to another, the kernel saves the first thread's registers, including its instruction pointer and stack pointer. Then it loads the second thread's saved registers. This is a context switch. If the new thread belongs to a different process, the kernel also switches which address space the hardware uses for translation OSTEP ch. 26.

The scheduler does not run your Rust code, and it does not know what compute or scores are. It decides whose instructions the core runs next. The core then runs those instructions until the kernel takes the core back, for example when the thread's time slice ends or when it waits for a file.

What can be different

Every mainstream desktop and server OS has processes, isolation and a scheduler. What a process record contains, how threads are created and how scheduling decisions are made all vary. Very small embedded systems may have no processes at all: one program, one address space, direct access to the hardware.

What to remember

  1. A program is a file; a process is one running instance with its own address space and resources.
  2. The same virtual address in two processes normally leads to different physical memory.
  3. The scheduler decides which thread runs on each core; it knows nothing about your Rust values.

Check your understanding

Two copies of the same program both print the address of a variable and get the same number. Do they share that variable?

No. Each address is virtual and belongs to one process's address space. The kernel normally connects it to different physical memory in each process. (In practice, address randomisation usually makes the numbers differ anyway.)

Why is it safe for both processes to use frame 3 for their code?

The code is mapped read-only. Neither process can change it, so sharing one physical copy cannot let one process affect the other.

Does the scheduler decide when a Rust value is dropped?

No. Dropping is decided by Rust's rules, and the compiler places the code for it in your program. The scheduler only decides which thread's instructions run on a core.
