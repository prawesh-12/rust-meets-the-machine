09Rust Compiler & runtime

Where does a Rust value live, and what does Box change?

Inside a function, values sit in registers or in the function's stack frame, and they are gone when the call returns. Some values have to outlive the call that made them, or are too large or too variable in size for a frame. Those values go on the heap, and a small value in the frame records where they are.

  • Compiler & runtime library
  • Operating system
  • CPU & hardware

Three different things: binding, value, storage

When you write let x = 7;, three separate things are involved:

  • The binding x: a name in your source code. It exists for the compiler. The running program has no names.
  • The value: the integer 7, of type i32, which the Rust rules talk about Rust.
  • The storage: wherever the compiled program keeps those 4 bytes while they are needed. That might be a register or a stack slot. It might be nowhere at all, if the compiler can fold the value into an instruction Compiler.

Rust's rules are about bindings and values: who owns a value, who may read it, when it is dropped. They say very little about storage. "Is x on the stack?" is a question about one build, not about the language Reference: type layout.

The heap is memory the allocator hands out

A frame lasts as long as its call. A value that has to outlive the call, or whose size is only known at run time, needs memory that is handed out and given back on request. That memory is the heap, and the code that hands it out is an allocator. Here "heap" only means a pool of memory handed out on request. It is unrelated to the heap data structure of the same name.

Rust has no memory of its own. The standard library uses one global allocator for Box, Vec, String and the rest std::alloc Runtime library. Which allocator that is by default is not specified.

On this Linux machine it behaved like the C library's malloc. Blocks came from the region marked [heap] in the process's memory map (/proc/self/maps). The C library got that region from the kernel OS malloc(3).

Box<T>: one pointer that owns one allocation

Box::new(7) "allocates memory on the heap and then places x into it" Box::new. What you get back is the box itself: a pointer to that allocation. For a sized type, a Box<T> "is guaranteed to be represented as a single pointer" std::boxed, which is 8 bytes on x86-64. The box owns the allocation: when the box is dropped, the 7 is dropped and the memory is given back to the allocator.

Here are three small values, each split into the four parts above:

examples/boxes.rs (shortened)
struct Pair { id: i32, score: Box<i32> }

let x = 7;
let b = Box::new(7);
let p = Pair { id: 1, score: Box::new(90) };

The numbers under the boxes come from one run of examples/boxes.rs, which looks each address up in /proc/self/maps proc_pid_maps(5). The program also printed size_of::<Box<i32>>() = 8 and size_of::<Pair>() = 16. The 16 bytes are 8 for the pointer, 4 for id, and 4 of padding. The padding makes the next Pair in an array start on an 8-byte boundary.

A struct holds its fields; a box points away

A Pair does not point to its id. The 4 bytes of id are inside the 16 bytes of Pair, wherever those are. Only score leads elsewhere, because its type is a box. In the default representation the compiler chooses the order of the fields and the padding; the order you wrote is not promised Reference: the Rust representation.

This difference matters when a value moves. Moving p to another binding copies its 16 bytes, including the 8-byte pointer; the 90 on the heap stays exactly where it is.

Why put something in a box?

  • The size is not known when compiling: a recursive type such as a tree node that contains another node, or a Box<dyn Trait>.
  • The value is large and you want moves to copy one pointer instead of the whole value.
  • The value should outlive the function that created it, without being returned by copy.

"Heap" does not mean "long-lived". A box made in a loop and dropped at the end of each iteration lives a few nanoseconds. The heap is a way of getting memory with an owner that decides when it is given back, not a promise about how long that is.

Three tempting pictures that are wrong

"Rust has its own memory." It uses the process's address space through an allocator, like any other program.

"Every local is on the stack." A local might be on the stack, in a register, or nowhere. Its owner is the binding; its storage is the compiler's choice.

"A box is on the heap." The box, the 8-byte pointer, sits wherever the binding's storage is. What it points to is on the heap.

What to remember

  1. A binding is a name, a value is what Rust's rules talk about, and storage is the compiler's choice.
  2. Heap memory comes from the global allocator, which gets it from the operating system.
  3. A Box<T> is one pointer that owns one heap allocation; dropping the box frees it.

Check your understanding

How many heap allocations does let p = Pair { id: 1, score: Box::new(90) }; make?

One, for the 90. The Pair itself, including id and the pointer, is stored wherever p is stored.

Can you rely on id being the first 4 bytes of a Pair?

No. With the default representation the field order is not guaranteed. #[repr(C)] fixes it, for code that needs that.

Is a Box<i32> 4 bytes or 8 on x86-64?

8: it is a pointer. The i32 it points to is 4 bytes, in a separate heap block.
