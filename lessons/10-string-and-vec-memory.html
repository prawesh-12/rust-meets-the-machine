10Rust Compiler & runtime

What is a Vec made of, and what happens when it grows?

A Box points to one value of a fixed size. A list such as scores holds a number of elements that changes while the program runs. A Vec does this with a small handle and a separate buffer that can grow. Several of Rust's rules exist because that buffer can move.

  • Rust language
  • Compiler & runtime library
  • Operating system
  • CPU & hardware

A handle and a buffer

A Vec<i32> value is three machine words Rust Library:

  • ptr: the address of a heap buffer;
  • len: how many elements are in use;
  • cap: how many elements fit in the buffer before it has to grow.

The documentation describes a Vec as "a (pointer, capacity, length) triplet", and says the order of those three fields is unspecified Vec: guarantees. On this machine size_of::<Vec<i32>>() is 24: three 8-byte words. The elements themselves are in the buffer, one after another with no gaps, which is why walking a Vec in order is cache-friendly.

The handle is stored wherever the scores binding is stored, typically main's frame. The buffer comes from the global allocator. The Vec owns the buffer: when scores is dropped, the elements are dropped and the buffer is freed.

What the run actually printed

From examples/vec.rs on this machine (addresses change on every run):

Output, shortenedfrom examples/OUTPUT.txt
len=2 cap=2 buffer at 0x562196998d50
len=3 cap=4 buffer at 0x562196998d50     ← grew in place
len=4 cap=4 buffer at 0x562196998d50     ← spare slot, no allocation
w: len=2 cap=2 buffer at 0x562196998d70  (neighbour at 0x562196998d90)
w: len=3 cap=4 buffer at 0x562196998d70
w: len=4 cap=4 buffer at 0x562196998d70
w: len=5 cap=8 buffer at 0x562196998db0  ← moved: the neighbour was in the way

The second vector, w, had a small allocation placed right after its buffer. Growing to 4 elements still fitted in its block; growing to 8 did not, and the buffer moved.

Whether a growth moves the buffer is up to the allocator. The C library's realloc describes both outcomes. The returned pointer "may be the same as p if the allocation was not moved (e.g., there was room to expand the allocation in-place)". Otherwise, "if the area pointed to was moved, a free(p) is done" malloc(3). What Vec itself promises is narrower: "push and insert will never (re)allocate if the reported capacity is sufficient" Vec: guarantees.

Why a reference into the buffer blocks push

Turn on Keep &scores[0] in the figure above and pick has to move. first holds the address of element 0. After the move, that address is inside a freed block: reading it would be a dangling pointer read. Rust does not wait to see which outcome happens. push takes &mut self, and a mutable borrow cannot overlap a shared one, so the compiler rejects the program in both cases with E0502 The Book §8.1. That rule is the heart of borrowing.

An empty Vec has no buffer

Vec::new() printed len=0 cap=0: nothing was allocated. The documentation guarantees that a vector with capacity 0 does not allocate Vec: guarantees. The first push allocates.

String is a Vec of UTF-8 bytes

A String has the same shape: pointer, length, capacity, 24 bytes on this machine. Its buffer holds bytes, and the bytes are always valid UTF-8 String: representation. len() counts those bytes, not characters:

String::from("hi"): len 2, 2 characters

104h105i

String::from("né"): len 3, 2 characters

110n195é, byte 1169é, byte 2

The bytes are from examples/vec.rs, which printed bytes=[110, 195, 169] for "né".

The text "hi" in the source is not a String. It is a &'static str: a pointer and a length referring to bytes stored inside the executable file, which are mapped read-only into the process's address space. String::from copies those bytes into a new heap buffer that the String owns and can grow The Book §4.1.

Four tempting pictures that are wrong

"Every push allocates." Only a push with len == cap does. The last push above allocated nothing.

"Growing always moves the buffer." In this run, the first growth stayed at the same address.

"The handle is ptr, then len, then cap." The order is unspecified.

"len() of a String is its number of characters." It is the number of bytes.

What to remember

  1. A Vec is a small handle (pointer, length, capacity) that owns a heap buffer of elements stored next to each other.
  2. A push with spare capacity writes into the buffer; a push without it gets a bigger block, which may be at a new address.
  3. Because the buffer can move, a reference into it cannot be held across a push.

Check your understanding

A Vec has len 3 and cap 4. Does the next push allocate?

No. There is one spare slot. The push after that would need a bigger block.

How many bytes does String::from("né") report as its length?

3: one byte for n and two for é in UTF-8.

If the allocator happened to grow the buffer in place, would first still be valid? Why does Rust reject the program anyway?

In that run it would still point at element 0. But the program cannot know beforehand which outcome it gets. The borrow rules are checked at compile time, so a shared borrow cannot overlap the mutable borrow that push needs.
