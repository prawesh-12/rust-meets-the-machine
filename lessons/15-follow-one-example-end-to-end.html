What happens, layer by layer, when total(&scores) runs?

A running program uses every layer at once: Rust's rules, values on the heap, a thread's stack, the address space and the CPU. Here the whole example program runs one event at a time, with every layer side by side. At each moment you can see which layer does the work, and which ones are not involved at all.

  • Rust language
  • Compiler & runtime library
  • Operating system
  • CPU & hardware
examples/sum.rsprints 60 
fn total(values: &Vec<i32>) -> i32 {
    let mut sum = 0;
    for v in values.iter() {
        sum += v;
    }
    sum
}

fn main() {
    let mut scores = vec![10, 20];
    scores.push(30);
    let t = total(&scores);
    println!("{t}");
}

What the optimised program actually does

The trace follows the source code. The binary built with -O is shorter. This is main from examples/OUTPUT.txt, with the formatting call left out Compiler:

x86-64, Intel syntax, symbol names shortenedfrom examples/OUTPUT.txt 
    mov   edi, 8
    mov   esi, 4
    call  __rust_alloc                 ; 8 bytes, aligned to 4: room for two i32
    movabs rcx, 85899345930            ; = 20·2³² + 10: both elements in one value
    mov   qword ptr [rax], rcx         ; one 8-byte store writes 10 and 20
    mov   qword ptr [rsp + 8], 2       ; handle: cap = 2
    mov   qword ptr [rsp + 16], rax    ;         ptr
    mov   qword ptr [rsp + 24], 2      ;         len = 2
    lea   rdi, [rsp + 8]
    call  RawVec::grow_one             ; push(30): len == cap, so grow
    mov   rbx, qword ptr [rsp + 16]    ; the (possibly new) buffer address
    mov   dword ptr [rbx + 8], 30      ; scores[2] = 30
    mov   eax, dword ptr [rbx]         ; total(): scores[0]
    mov   ecx, dword ptr [rbx + 4]     ;          scores[1]
    add   eax, ecx
    add   eax, 30                      ; scores[2] is known to be 30
    …                                  ; println!("{t}")
    call  __rust_dealloc               ; drop(scores): free cap·4 = 16 bytes

This short listing shows several layers at work, and the gap between the language and the machine:

  • There is no total function in the binary at all, and no iterator: the loop became two loads and an addition. The compiler only has to preserve what the program prints, so it inlined the call.
  • The handle was laid out as cap, ptr, len in this build. That is allowed because the order is unspecified.
  • The heap allocation is real: __rust_alloc, grow_one and __rust_dealloc are the global allocator's entry points, and the dealloc call is where the drop happens.
  • The borrow checker left no trace. &scores became an address in a register, and the rules that made it safe were checked before the program existed.

Which layer decides what

Question Decided by When
May push run while first is alive? Rust borrow checker compile time
Is sum in a register or in a stack slot? Compiler compile time
Where is the buffer, and does it move when it grows? Allocator run time
Which physical frame holds the buffer's page? OS kernel run time, on first touch
Which thread runs, and on which core? OS scheduler run time
Is the line in L1, and is the translation in the TLB? Hardware run time, every access

What to remember

  1. Rust's ownership and borrowing rules act at compile time; at run time there are only addresses, loads and stores.
  2. The compiler, the allocator, the kernel and the hardware each make their own decisions about the same few bytes.
  3. The source describes behaviour; the binary may look very different and still behave the same.

Check your understanding

In the optimised binary, at which instruction is scores dropped?

The call __rust_dealloc near the end of main: that frees the buffer, which is all a Vec<i32>'s drop has to do.

Which layer turns the virtual address of scores[0] into a physical one?

The MMU in the CPU, using page tables the kernel set up. On a TLB hit, the kernel is not involved at all.

Does the borrow &scores cost anything at run time?

Only what any address costs: at most one register or a few bytes of stack. The checking happened during compilation. Here the compiler removed even that by inlining total.
